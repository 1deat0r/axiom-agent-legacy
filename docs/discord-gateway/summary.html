Gateway breadth — summary

Issue #3 — gateway breadth, both halves: <b>more transports</b> (Discord, Slack) and <b>continuity</b> (a delivery ledger + fan-out so one run reaches every channel). Discord and Slack each reuse the Telegram per-channel-cursor shape and wire into the SAME channel index + sender allowlist; a delivery ledger records every outbound delivery and <code>/announce</code> fans one message to every configured channel.

1Goal & assumptions

  • Discord + Slack receive via REST long-poll per channel (snowflake / message-ts cursor), not websocket; websocket realtime is a follow-up.
  • channelId = platform channel id (drives the channel index); sender = author/user id (drives the shared config.json allowlist).
  • Slack reports errors as HTTP 200 <code>ok:false</code> bodies (like Telegram); fatal set = invalid_auth/not_authed/account_inactive/token_revoked. Discord fatal = 401.
  • Ledger is single-writer JSONL under the gateway dir; fan-out is single-transport (the router owns one transport). Cross-platform fan-out + cron spine feeding are follow-ups.

3Key decisions

  • Selection: --transport discord|slack + tokens; missing token fails fast; default stays signal; unknown values error.
  • Receive: per-channel cursor long-poll; cursors persisted (discord/slack-cursor.json) for no-replay; Slack's inclusive oldest filtered to strict-greater ts.
  • Identity: channel id -> channel index; author/user id -> allowlist gate.
  • Per-channel isolation + fatal: channel 403/429/5xx / ok:false channel_not_found logged+skipped; only fatal token errors stop the loop.
  • Chunking: reuse the shared chunker at Discord 2000 / Slack 40,000 caps.
  • Continuity: every outbound delivery (reply, denial, fan-out) passes one deliver() path and is recorded; deliverToAll() sends to every config deliverTo channel; commands stay sync (fire-and-forget fan-out).
