Discord transport — summary

Add a Discord transport to the axiom gateway reusing the Telegram transport's shape, wired into the SAME channel index + sender allowlist, so <code>axiom gateway --transport discord --discord-token X</code> boots it. First step of issue #3 (Gateway breadth — more transports + continuity).

1Goal & assumptions

  • Discord receive is REST long-poll (per-channel <code>getMessages?after=cursor</code>), not websocket — mirrors Telegram's getUpdates long-poll; websocket low-latency is a follow-up.
  • channelId = Discord channel id; sender = author id (snowflake) — gated by the shared config.json allowlist; channel index maps channel→session.
  • Bot polls every message-capable channel it can see (DM + guild text/news), like Telegram's deliver-everything.
  • Delivery ledger / Slack / fan-out: out of scope for this first step.

3Key decisions

  • Selection: --transport discord + --discord-token/AXIOM_DISCORD_BOT_TOKEN; unknown value errors; missing token fails fast; default stays signal.
  • Boundary: DiscordClient (sendMessage / listChannels / getMessages) with an AbortSignal; HttpDiscordClient exercised only against a local server.
  • Receive: per-channel snowflake cursor long-poll; cursor persisted to <AXIOM_HOME>/gateway/discord-cursor.json for no-replay.
  • Identity: channelId = channel id (drives channel index); sender = author id (drives the allowlist gate).
  • Per-channel isolation: a channel 403/429/5xx is logged (throttled) and skipped; only 401 (bad token) is fatal.
  • Chunking: reuse the Telegram chunker at Discord's 2000-char cap.
